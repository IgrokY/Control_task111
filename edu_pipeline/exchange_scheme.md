# Схема обмена данными и выбор формата

## 1. Цепочка обмена

```
enrollments_raw.csv ──► ETL (валидация) ──► edu.db
                                              │
                                   SQL-агрегат по курсам и статусам
                                              │
                                   внутренняя модель: list[dict]
                                        ┌─────┴─────┐
                                        ▼           ▼
                                   report.json   report.xml
                                        │           │
                                 внешняя система A  внешняя система B
                                        │           │
                                   read_json()  read_xml()
                                        └─────┬─────┘
                                              ▼
                                   сравнение с моделью (==)
```

Отдельный поток — ответ внешней системы:

```
HTTP-ответ (текст)
      │
      ├─ пусто? ─────────────────► error: empty_response
      ├─ начинается с «<»? ──────► error: html_response (проверка ДО json.loads)
      ├─ json.loads упал? ───────► error: invalid_json
      ├─ не объект? ─────────────► error: unexpected_type
      ├─ нет обязательного поля? ► error: missing_field
      └─ иначе ──────────────────► ok: data
```

## 2. Внутренняя модель

Одна строка агрегата:

```python
{
    "course_code": "PY-100",
    "status": "enrolled",
    "enrollments": 3,
    "hours": 108.0,
    "revenue": 135000
}
```

Модель — список таких словарей. Оба формата преобразуются именно к ней, поэтому
сравнение `from_json == internal == from_xml` доказывает эквивалентность выгрузок.

## 3. JSON

```json
{
  "report": "enrollments_by_course_status",
  "rows": [
    {"course_code": "PY-100", "status": "enrolled",
     "enrollments": 3, "hours": 108.0, "revenue": 135000}
  ]
}
```

* типы сохраняются: число остаётся числом, `null` — отсутствием значения;
* вложенность выражается естественно;
* `ensure_ascii=False` сохраняет кириллицу читаемой;
* размер файла больше XML, но парсинг проще.

## 4. XML

```xml
<?xml version='1.0' encoding='utf-8'?>
<report name="enrollments_by_course_status">
  <row>
    <course_code>PY-100</course_code>
    <status>enrolled</status>
    <enrollments>3</enrollments>
    <hours>108.0</hours>
    <revenue>135000</revenue>
  </row>
</report>
```

* всё хранится текстом: при чтении нужен явный словарь `NUMERIC_FIELDS`,
  иначе `enrollments` вернётся строкой `"3"`;
* удобен для строгой схемы (XSD), атрибутов и legacy-систем;
* `ET.indent` делает файл читаемым для человека.

## 5. Когда что практичнее

| Критерий | JSON | XML |
|---|---|---|
| Типы данных | сохраняются | всё текст, нужен разбор |
| Читаемость | высокая | средняя из-за тегов |
| Размер | меньше | больше в 2–3 раза |
| Схема и валидация | JSON Schema | XSD, зрелее в enterprise |
| Атрибуты и пространства имён | нет | есть |
| Типовой потребитель | веб-сервисы, JS/Python | банки, госсервисы, SOAP |
| Разбор в Python | `json` | `xml.etree.ElementTree` |

Вывод: для внутреннего обмена и REST — JSON; для внешних контрактов, где нужна
формальная схема или уже есть SOAP-интеграция, — XML.

## 6. Правила безопасной обработки ответа

1. Сначала проверить, что ответ непустой.
2. Проверить, что он не начинается с `<`: HTML-страница ошибки (например,
   `502 Bad Gateway` из `api_response_error.html`) — не JSON.
3. Только потом вызывать `json.loads` в `try/except JSONDecodeError`.
4. Проверить тип: ожидается объект, а не массив.
5. Проверить обязательные поля `status` и `rows_received`.
6. При любой проблеме вернуть код причины, а не падать с трейсбеком.

Именно такой порядок реализован в `safe_parse_external()` модуля `export_data.py`.
